napari プラグイン作成の要点

このノートの目的

このノートは、napari 公式ドキュメントの Building a plugin をもとに、leaf-vein-workflow のような napari plugin を作るときの基本構造を整理したものです。

対象は、現在の leaf-vein-workflow と同じく、napari のメニューから dock widget を開いて画像処理ワークフローを進めるタイプの plugin です。

公式ドキュメント上の位置づけ

napari plugin は、napari の機能を Python package として拡張する仕組みです。公式ドキュメントでは、主に次のような拡張が想定されています。

種類 何を追加するか
reader 新しいファイル形式の読み込み
writer napari レイヤーの保存
widget 独自の UI や処理パネル
sample data File > Open Sample から開けるサンプルデータ
theme napari の見た目

leaf-vein-workflow は、このうち widget plugin です。画像の読み込み自体は napari 標準機能に任せ、plugin は ROI、Gaussian smoothing、mask の作成と cleanup、order labels の作成を担当します。

最小構成

公式チュートリアルでは、現在の新しい plugin 形式として npe2 を対象にしています。napari plugin は通常の Python package ですが、少なくとも次の 2 つが必要です。

  1. plugin の貢献内容を静的に書いた manifest ファイル
  2. napari が manifest を見つけるための napari.manifest entry point

この repo では、それぞれ次のファイルが対応しています。

役割 この repo のファイル
package metadata と entry point pyproject.toml
plugin manifest src/leaf_vein_workflow/napari.yaml
manifest から参照する互換用入口 src/leaf_vein_workflow/_widget.py
1 つの widget の組み立て src/leaf_vein_workflow/widgets/crop_widget.py
工程別の widget 実装 src/leaf_vein_workflow/widgets/ 以下の各モジュール

pyproject.toml で napari に見つけてもらう

napari は、インストール済み Python package の entry point を見て plugin を発見します。この repo では次の部分が対応しています。

[project.entry-points."napari.manifest"]
leaf-vein-workflow = "leaf_vein_workflow:napari.yaml"

左辺の leaf-vein-workflow は plugin の配布名です。右辺は、Python package leaf_vein_workflow の中にある napari.yaml を manifest として読む、という意味です。

また、PyPI や napari hub 上で napari plugin として認識されやすくするため、package metadata には次の classifier を入れます。

classifiers = [
    "Framework :: napari",
]

この repo ではすでに Framework :: napari が入っています。

napari.yaml で何を提供するかを書く

manifest には、plugin が napari に提供する機能を書きます。公式ドキュメントでは、まず commands を定義し、その command を widget、reader、writer、menu などから参照する形が基本です。

この repo の napari.yaml は、widget を 1 つ提供します。

name: leaf-vein-workflow
display_name: Leaf Vein Workflow
contributions:
  commands:
    - id: leaf-vein-workflow.make_crop_widget
      title: Make ROI Crop Widget
      python_name: leaf_vein_workflow._widget:CropWidget
  widgets:
    - command: leaf-vein-workflow.make_crop_widget
      display_name: Leaf Vein Workflow

ここで重要なのは、commands と widgets の対応です。

項目 意味
id command の一意な ID。plugin 名から始める
title command の説明名
python_name 実際に呼び出す Python オブジェクト
widgets.command widget として開く command
display_name napari の plugin menu に表示される名前

この設定により、napari の Plugins menu から Leaf Vein Workflow を選ぶと、leaf_vein_workflow._widget:CropWidget が作られます。_widget.py は widgets/crop_widget.py の CropWidget を再公開する薄い入口なので、内部を分割しても manifest の python_name と既存の import は変わりません。

widget 実装の考え方

widget contribution は、napari の画面に独自の操作パネルを追加する仕組みです。公式ドキュメントでは、widget は Qt の QWidget、magicgui の widget、または自動生成 widget として提供できます。

この repo では Qt widget を直接使っています。napari に提供する widget は 1 つのままですが、クラスの実装を 1 ファイルにまとめる必要はありません。

# src/leaf_vein_workflow/_widget.py
from .widgets.crop_widget import CropWidget

# src/leaf_vein_workflow/widgets/crop_widget.py
class CropWidget(QWidget):
    def __init__(self, napari_viewer):
        super().__init__()
        self.viewer = napari_viewer

napari_viewer を受け取ることで、widget から viewer の layer list にアクセスできます。現在の実装では、次の処理を viewer API 経由で行います。

  • 新しい Image layer を見つける
  • ROI 用 Shapes layer を追加する
  • crop Image layer を追加または更新する
  • smoothed_image Image layer を追加または更新する
  • vein_mask と order_labels の Labels layer を追加または更新する

1 つの widget を責務別に分ける

CropWidget は全体を組み立てる場所として残し、具体的な処理は次のファイルに分けています。

ファイル 主な責務
widgets/crop_widget.py widget の組み立て、Qt signal の接続、公開メソッドから各工程への委譲
widgets/controls.py UI 部品の生成、レイアウト、工程に応じた有効・無効の切り替え
widgets/layers.py metadata 定数、レイヤー間の対応、検索、選択、削除
widgets/roi.py Image layer の検出、ROI の準備と確認、crop の作成
widgets/mask.py Gaussian、Otsu、閾値 timer、mask cleanup
widgets/order_labels.py order labels の作成、再利用、mask 外への描画防止

各工程の担当は互いを直接呼び合わず、共有する controls とレイヤー管理を CropWidget から受け取ります。たとえば order labels のコードが ROI 内部の辞書を直接読むことはありません。依存方向を単純にすることで、ある工程を修正するときに別工程の実装まで読み込まずに済みます。

既存の CropWidget.add_roi()、apply_gaussian_filter()、use_otsu_threshold()、clean_mask()、create_order_labels() は薄い委譲メソッドとして残します。napari の見た目と外部からの呼び方を保ちながら、内部だけを分割するためです。

コードを読むときは、まず _widget.py で公開入口を確認し、次に crop_widget.py で全体の接続を見ます。その後、UI なら controls.py、レイヤーの active/visible や削除なら layers.py、個別の操作なら roi.py、mask.py、order_labels.py の該当ファイルだけを読みます。配列計算の詳細は、そこから呼ばれる crop.py、threshold.py、order.py を確認します。

contribution の種類を選ぶ

plugin を作るときは、最初に「napari のどこを拡張したいのか」を決めます。

目的 選ぶ contribution
独自フォーマットを開きたい reader
レイヤーを独自形式で保存したい writer
操作パネルを出したい widget
メニュー項目を追加したい menu
デモ用画像を同梱したい sample data

leaf-vein-workflow の MVP では、まず widget だけで十分です。画像ファイルの読み込みは napari に任せられるため、reader を追加する必要はまだありません。

将来、葉脈解析用の独自 project file を読み書きする段階になったら、reader や writer の追加を検討します。その場合も、GUI から無理にファイル形式を扱うより、reader/writer contribution として分けた方が napari の作法に合います。

dependency の注意点

公式の best practices では、plugin の依存関係を重くしすぎないことが強調されています。特に Qt backend への依存は避けるべきです。

避けたい例:

  • runtime dependency に napari[all] を入れる
  • runtime dependency に PyQt5、PyQt6、PySide6 を固定する
  • wheel がない重い binary dependency を安易に増やす

この repo では、Qt backend の pyqt6 は dev dependency に置いています。plugin の利用者がどの Qt backend を使うかは、基本的に利用者側の napari 環境に任せる方が安全です。

また、型注釈だけのために napari を import する場合は、文字列 annotation や typing.TYPE_CHECKING を使うと runtime dependency を増やさずに済みます。ただし、この repo は napari.layers や通知 API を runtime で使うため、napari dependency は実際に必要です。

テスト方針

公式ドキュメントでは、napari plugin のテストには pytest が推奨されています。また、viewer を使うテストには make_napari_viewer_proxy fixture が用意されています。

一方で、すべてを napari の画面操作として統合テストする必要はありません。公式 docs でも、小さい unit test に分けることが勧められています。

この repo の方針は次の通りです。

対象 テスト方針
crop 計算 tests/test_crop.py で NumPy 配列として直接テスト
Gaussian、threshold、cleanup 計算 tests/test_threshold.py で直接テスト
order labels の検証・集計 tests/test_order.py で直接テスト
widget と napari layer tests/test_widget_import.py で import 互換性と明示的な工程を統合確認

この分け方にすると、GUI や Qt の不安定さに引きずられず、画像処理の仕様を小さく確認できます。

開発中の確認手順

ローカルで plugin を変更したら、まず editable install 相当の環境で napari を起動して確認します。この repo では uv を使うため、基本コマンドは次の通りです。

uv sync
uv run napari

napari が起動したら、次を確認します。

  1. Plugins > Leaf Vein Workflow > Leaf Vein Workflow から widget が開く。
  2. 画像を開くと ROI 用 Shapes layer が作られる。
  3. Add ROI で crop が作られる。
  4. Apply Gaussian では smoothed_image だけが作られ、まだ vein_mask がない。
  5. Apply Otsu で初めて vein_mask が作られ、閾値を調整できる。
  6. Clean Mask 後も paint mode で手動修正できる。
  7. 手動修正後の Create Order Labels で order_labels が作られ、mask 外には描画できない。

自動テストは次で実行します。

uv run pytest

公開するときの流れ

公式ドキュメントでは、公開先として PyPI、conda-forge、napari hub が挙げられています。

基本的な流れは次の通りです。

  1. Framework :: napari classifier を package metadata に入れる。
  2. pyproject.toml と napari.yaml が正しく入った配布物を作る。
  3. PyPI に公開する。
  4. napari hub 上の説明文や metadata を整える。
  5. 必要なら conda-forge にも公開する。

新規 plugin を最初から作る場合は、公式の napari-plugin-template を使うと、package 構成、テスト、CI、公開設定の雛形を作れます。ただし、既存 repo で小さく育てる場合は、今のように pyproject.toml、napari.yaml、widget 実装、tests を確認しながら足していく方が追いやすいです。

この repo で次に見直す場所

プラグイン作成の観点では、今後の変更時に次を確認するとよいです。

確認点 見る場所
napari が plugin を発見できるか pyproject.toml の napari.manifest
menu に出る名前が適切か src/leaf_vein_workflow/napari.yaml
manifest と import の互換性が保たれているか src/leaf_vein_workflow/_widget.py
signal と工程の接続が明示されているか widgets/crop_widget.py
layer の対応・選択・削除が一元管理されているか widgets/layers.py
各操作の修正範囲が工程別に分かれているか widgets/roi.py、widgets/mask.py、widgets/order_labels.py
計算処理が GUI から分離されているか crop.py、threshold.py、order.py
napari なしで確認できる仕様がテストされているか tests/test_*.py
