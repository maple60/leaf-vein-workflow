Leaf Vein Workflow の挙動と関数の流れ

このノートの目的

このノートは、leaf-vein-workflow の現在の MVP 実装について、人間が読んで流れを理解するための説明です。

このプラグインが今やることは、次の 4 段階に絞られています。

  • DPI、µm/px、mm/px、または手動で引いたスケールバー線から、元画像ごとの mm/px を校正する。
  • napari で画像を開き、長方形 ROI を 1 つ描き、Add ROI ボタンを押したときだけ、その範囲の切り抜き画像レイヤーを作る。
  • 切り抜き画像に Gaussian smoothing を適用し、Otsu 閾値で葉脈候補の mask Labels レイヤーを作り、形態学的処理と手作業で整える。
  • 確認済みの mask Labels レイヤーから、手動分類用の order labels レイヤーを作る。
  • 次数ごとの骨格長と、確定した標本の葉身面積（または明示した外部入力面積）に対する VLA を計算し、export する。

まだ扱わないことは、スケールバーの OCR・自動検出、複数 ROI、ポリゴン ROI、画像の保存、nD stack、次数の自動分類、minor（4次以上）のラベルです。

ユーザーから見た流れ

dock は次の6つの手順に番号付きで並び、各手順の先頭に1行の操作説明があります。

手順 dock の表示 やること
1 1. Image & scale 画像を読み込み、スキャン解像度で校正する
2 2. ROI 解析する範囲を長方形で選ぶ
3 3. Vein mask mask を作って葉脈の領域を確定する（後片付けの処理も同じ手順内）
4 4. Paint vein orders 葉脈を次数ごとに塗り分ける
5 5. Leaf area & VLA 確定したROIの葉身面積を使う。外部面積は明示的に切り替えて入力（VLA は Export 時に計算）
6 6. Export 出力先を選んで書き出す

1次・2次脈のパス計測（vein_paths.py）は実装済みですが、今は dock に表示していません。

細かい操作は次の順番になります。

  1. napari を起動する。
  2. Plugins > Leaf Vein Workflow > Leaf Vein Workflow から widget を開く。
  3. napari 標準の方法で葉画像を開く。
  4. DPI、µm/px、mm/px の値を入力して Apply Scale を押す。または Scale bar を選び、Draw Scale Bar Line でバーに線を1本引き、実長を入力して校正する。校正しない場合は pixel 単位のまま続行できる。
  5. プラグインが自動で作った ROI 用 Shapes レイヤーに長方形を 1 つ描く。
  6. Add ROI ボタンを押し、切り抜いた Image レイヤーを作る。
  7. Gaussian sigma を確認して Apply Gaussian を押す。
  8. 平滑化した smoothed_image Image レイヤーだけが作られる。
  9. Apply Otsu で leaf_mask の候補を作る。葉柄・異物・輪郭を手修正し、Confirm Leaf & Extract Veins を押すと葉身面積を計算し、その領域内で2段階目のOtsuを実行して vein_mask を作る。
  10. 色の付いた画素（黄色）が葉脈。Otsu は少ない側を葉脈として選び、Invert (dark pixels are vein) を自動で合わせる。必要なら Invert と Mask threshold を調整する。変更後、少し待つと同じ mask レイヤーが更新される。
  11. 形態学的処理の値を確認して Clean Mask を押す。
  12. paint mode の vein_mask を手作業で修正する。
  13. mask を確認した後に Create Order Labels を押す。
  14. （任意）Mark Base & Apex で葉の基部と1次脈の先端をクリックする（2点目で order_labels の塗る状態に戻る）。Auto-assign 1°/2° で1次・2次脈を自動で塗り、残りの脈は太さで3次脈（太い側）と不確定（細い側）に分ける。進み具合は dock 下部のバーに出る。不確定（4）の画素だけを書き換えるので、手で塗った所は残る。
  15. 葉脈の画素はすべて 4（不確定、紫）から始まる。Paint as で 1°・2°・3°・Uncertain を選び（色見本はラベルの色と同じ）、画像上の葉脈をドラッグして塗る。mask の外は塗られない。ブラシの太さは napari の layer controls（左上）で変える。napari 側でラベル番号を変えても Paint as が追従する。
  16. 5. Leaf area & VLA では確定時に選ばれる Confirmed leaf mask (current ROI) を使う。別途測定した面積を使う場合だけ External area (manual input) を選んで入力し、単位（mm² / cm²）を指定する。
  17. 6. Export の Export Measurements を押すと、現在のラベルを計測して出力フォルダに CSV・ラベル（.npy）・QC 画像・branch table を書き出す。出力先の既定は napari を起動したフォルダ直下の output/ で、Change... で変えられる。結果は dock には表示せず、書き出し完了と未分類ピクセルの警告を通知で出す。

dock の各工程は同時に1つだけ開き、Apply Scale・Add ROI が成功すると次の工程が自動で開く。Create Order Labels の後は塗り分けが続くので、手順4は開いたままにする。

重要なのは、各工程がユーザーの操作で明示的に区切られている点です。長方形を描いただけでは crop は作られず、Apply Gaussian を押しても vein_mask は作られません。Apply Otsu は葉身候補だけを作り、葉脈maskは葉身の確定後に作られます。

スケール校正

どの入力方法でも、内部では mm_per_pixel に統一します。DPI の場合は 25.4 / DPI、µm/px の場合は値を 1000 で割って mm/px に変換します。スケールバー方式では、専用の Shapes レイヤーに引いた2点の線の pixel 長と、入力した実長から mm/px を求めます。線がない、2本以上ある、実長が0以下である場合は校正を確定しません。

確定した値、入力方法、元の入力値と単位は元画像の metadata に保存され、crop、smoothed_image、vein_mask、order_labels に引き継がれます。再校正すると既存の派生レイヤーも更新されます。ステータスには入力方法に関係なく µm/px、mm/px、mm/px から逆算した等価 DPI を併記します。表示座標と ROI の切り抜き計算を壊さないため、napari の layer scale 自体は変更しません。

校正を確定すると、画像の左下にマゼンタの表示用スケールバー（<画像名> 10 mm bar）を描きます。画像幅の 40% に 10 mm が収まらない小さい画像では、5・2・1 mm、500・200・100 µm の順に短いバーを使います。定規と見比べて校正値が正しいか目で確かめるためのもので、計測には使いません。再校正すると同じレイヤーを更新し、作業中のレイヤー選択は変えません。

校正済みの skeleton.py helperには、従来のpx列に加えて長さ・直径・局所座標のmm列が追加されます。未校正なら従来どおりpx列だけです。次数別計測の order.py は既存の pixel_size_mm 引数で、長さmm、葉面積mm²、VLA（mm mm(^{-2})）を計算します。

全体像

napari 上では 1 つの dock widget ですが、実装は人間が担当範囲を追いやすいように責務別に分かれています。

ファイル 役割
src/leaf_vein_workflow/_widget.py manifest と既存 import のために CropWidget と定数を再公開する入口
src/leaf_vein_workflow/widgets/crop_widget.py 1 つの widget を組み立て、signal を接続し、公開メソッドを各担当へ委譲する
src/leaf_vein_workflow/widgets/controls.py ボタンや入力欄を作り、工程ごとの有効・無効を管理する
src/leaf_vein_workflow/widgets/layers.py metadata、レイヤー間の対応、検索、選択、削除を一元管理する
src/leaf_vein_workflow/widgets/calibration.py 校正UIの操作、スケールバー線、元画像ごとのmetadata反映を担当する
src/leaf_vein_workflow/widgets/roi.py 画像の検出、ROI Shapes レイヤー、crop の作成を担当する
src/leaf_vein_workflow/widgets/mask.py Gaussian、Otsu、閾値更新、Clean Mask を担当する
src/leaf_vein_workflow/widgets/order_labels.py order labels の作成と mask 外への描画防止を担当する
src/leaf_vein_workflow/crop.py 画像配列をどこで切るかを計算する
src/leaf_vein_workflow/calibration.py DPI・直接値・スケールバーを mm/px に変換する
src/leaf_vein_workflow/threshold.py grayscale 化、Gaussian、閾値、mask cleanup を NumPy 配列に対して計算する
src/leaf_vein_workflow/order.py order labels の検証、集計、export に使う napari 非依存の処理を置く

初心者向けに言うと、_widget.py は変わらない「玄関」、crop_widget.py は全体をつなぐ「進行係」、widgets/ の残りは工程別の「担当者」です。crop.py、threshold.py、order.py は napari の画面を直接触らない「計算の係」です。

napari への登録

napari は src/leaf_vein_workflow/napari.yaml を読んで、このパッケージの widget を見つけます。

このファイルでは、leaf_vein_workflow._widget:CropWidget が widget として登録されています。つまり napari のメニューからプラグインを開くと、CropWidget クラスが作られます。

CropWidget の初期化

CropWidget は、napari に渡す 1 つの dock widget です。実際のクラスは widgets/crop_widget.py にあり、_widget.py は従来と同じ import 先を保つためにそれを再公開します。

作られた直後に、主に次の準備をします。

  • napari viewer を self.viewer に保存する。
  • controls.py でボタン、入力欄、ステータス表示を作る。
  • layers.py で scale bar、ROI、crop、smoothed image、mask、order labels の対応関係を管理する。
  • calibration、ROI、mask、order labels の各担当に、共有する controls とレイヤー管理を明示的に渡す。
  • crop_widget.py でボタンや Qt signal を各担当の処理へ接続する。
  • 新しく追加された画像と、すでに開かれている画像の両方を ROI 担当に渡す。

CropWidget の add_roi()、apply_gaussian_filter()、use_otsu_threshold()、clean_mask()、create_order_labels() は、既存コードやテストから同じ名前で呼べます。ただし実処理は対応する工程モジュールへ委譲されます。これにより、画面は 1 つのままでも、修正時に読む範囲を絞れます。

画像が追加されたとき

画像レイヤーが追加されると、crop_widget.py がその event を roi.py の画像準備処理へ渡します。

ROI 担当は、次の確認をします。

  1. 追加されたレイヤーが napari の Image レイヤーか。
  2. その画像が、プラグイン自身が作った crop レイヤーではないか。
  3. すでに ROI レイヤーと結びついている画像ではないか。

この確認を通った画像だけに、ROI 用の Shapes レイヤーを作ります。

ROI レイヤーには、metadata として次の情報が入ります。

metadata 意味
leaf_vein_workflow_role = roi_shapes この Shapes レイヤーは ROI 用である
source_image = 元画像名 どの画像から作られた ROI か

さらに、layers.py のレイヤー管理が、ROI レイヤーと元画像レイヤーの対応を保存します。各工程が個別の対応表を持たないため、派生レイヤーを探す規則や削除する順序を 1 箇所で確認できます。

ROI が編集されたとき

ユーザーが ROI を描いたり編集したりすると、roi.py の ROI 確認処理が呼ばれます。

ここで確認しているのは、主に次の 2 点です。

  • ROI が 1 つだけあるか。
  • その ROI が長方形か。

ROI が 0 個、または 2 個以上ある場合は、ステータス表示で「長方形を 1 つだけ描いてください」と案内します。長方形以外の場合は、警告を出します。

ただし、この段階ではまだ画像を切り抜きません。ここでは「準備ができたか」を確認しているだけです。

Add ROI を押したとき

Add ROI ボタンを押すと、公開メソッド CropWidget.add_roi() が roi.py の切り抜き処理へ委譲します。

ROI 担当は、まず次の順番でチェックします。

  1. 現在選択されているレイヤーが ROI 用 Shapes レイヤーか。
  2. その ROI レイヤーが元画像と結びついているか。
  3. ROI が 1 つだけか。
  4. ROI が長方形か。
  5. ROI が画像と重なっているか。

すべて通った場合だけ、実際の切り抜き処理に進みます。

切り抜き処理では、rectangle_to_slices() と crop_to_rectangle() の 2 つを使います。

rectangle_to_slices()

rectangle_to_slices() は、ROI の頂点座標を NumPy の slice に変換する関数です。

たとえば、長方形 ROI の座標がだいたい次の範囲だったとします。

座標 値
y の最小値 1.2
y の最大値 3.7
x の最小値 2.1
x の最大値 4.9

この場合、関数は次のように整数の範囲へ変換します。

軸 変換後
y slice(1, 4)
x slice(2, 5)

最小値側は floor で下に丸め、最大値側は ceil で上に丸めます。これにより、ROI に含まれる画素を取りこぼしにくくしています。

また、ROI が画像の外にはみ出している場合は、画像の範囲内に切り詰めます。完全に画像と重ならない場合は、エラーにします。

対応している画像は、現在の MVP では次の 2 種類です。

  • 2D grayscale image
  • 2D RGB/RGBA image

crop_to_rectangle()

crop_to_rectangle() は、実際に画像配列を切り抜く関数です。

内部では、まず rectangle_to_slices() を呼び出して、切り抜く y 範囲と x 範囲を決めます。その後、画像が 2D なら次のように切ります。

image_array[y_slice, x_slice]

RGB/RGBA のように最後の軸が色チャンネルの場合は、色チャンネルを残すために次のように切ります。

image_array[y_slice, x_slice, :]

戻り値は .copy() された配列です。これは、元画像の一部を参照するのではなく、切り抜き画像として独立したデータにするためです。

crop レイヤーの作成と更新

ROI 担当は、切り抜いた画像を napari の Image レイヤーとして追加します。

新規作成時には、次の情報を指定します。

  • レイヤー名は 元画像名 ROI
  • RGB/RGBA 画像なら rgb=True
  • translate に ROI の左上位置を入れる
  • metadata に crop レイヤーであることを記録する

translate を設定する理由は、切り抜き画像を元画像上の ROI 位置に重ねて表示しやすくするためです。

同じ ROI レイヤーからすでに crop レイヤーが作られている場合は、新しいレイヤーを増やさず、既存レイヤーの data と translate を更新します。

crop を作り直した場合は、古い crop から派生した smoothed_image、vein_mask、order_labels を削除します。新しい範囲に古い解析結果が残らないようにするためです。その後、crop を active layer にし、元画像を非表示にします。

mask レイヤーの作成と更新

mask 処理は widgets/mask.py が担当し、Apply Gaussian、Apply Otsu、Clean Mask という明示的な工程に分かれています。

Apply Gaussian は、現在の crop Image レイヤーに threshold.py の smooth_image() を適用し、smoothed_image Image レイヤーだけを作成または更新します。この時点では vein_mask を作りません。Gaussian sigma の初期値は 1 で、必要に応じて実行前に変更できます。

Apply Otsu は、平滑化済み画像に estimate_leaf_mask() を適用し、1段階目の葉身候補を編集可能な leaf_mask Labelsとして表示します。

  • ROI includes background (paper) が有効なら、ROIの縁に多く、その大部分が縁につながるクラスを背景とみなします。
  • 背景を検出できない場合、または背景除外がオフの場合は、ROI全体を候補として表示します。局所ROIの面積を全葉面積とは扱いません。
  • 葉柄や異物を消し、輪郭や穴の扱いを確認して Confirm Leaf & Extract Veins を押します。確定したマスクの画素数に校正値（mm/px）の二乗を掛けて面積を求め、同じマスク内で estimate_vein_threshold(..., leaf_mask=...) を実行します。
  • 少ない側のクラスを葉脈として Invert を合わせ、vein_mask を作ります。葉身マスクは非表示にして残します。未校正の場合は面積をpx²で表示し、物理単位のVLAは求めません。

確定後に葉身を変更した場合、再確定するまで閾値による再抽出と測定・Exportを止めます。再確定では既存の葉脈maskと次数ラベルを置き換えるため、手修正が失われることを確認するダイアログを表示します。ROIを再作成すると葉身の確定状態も解除されます。校正を変更した場合は新しい値で面積を計算します。

葉身候補の穴は自動では埋めません。実際の欠損か、背景に似た染色むらかを確認して手修正します。

Invert threshold が有効な場合は、閾値以下の画素を 1 として扱います。これは、葉脈が背景より暗い画像で使う想定です。

一度 Confirm Leaf & Extract Veins を実行した後は、閾値入力欄、slider、Invert threshold の変更に応じて同じ mask を更新します。連続した UI signal ごとに重い処理を繰り返さないよう、短い待ち時間を置く single-shot timer で更新をまとめます。この timer にも「葉身確定済み」の確認があり、control の初期化や Apply Gaussian だけで mask が作られることを防ぎます。

mask は napari の Labels レイヤーとして作られます。レイヤー名は vein_mask です。同じ crop レイヤーからすでに mask が作られている場合は、新しいレイヤーを増やさず、既存 mask レイヤーの data と translate を更新します。

Clean Mask は、small object removal、hole filling、closing、opening の設定を postprocess_mask() に渡し、現在の mask を明示的に整えます。入力欄は従来どおり整数pxですが、校正済み画像では small object と hole の面積をmm²、closing と opening の半径をµmまたはmmでラベルに併記します。値の変更、再校正、別画像への切り替えに応じて換算表示も更新されます。未校正画像ではpxだけを表示します。cleanup 後は自動の閾値更新を止め、vein_mask を active な paint mode に保ちます。これにより、その後の手作業による修正が遅延 timer で上書きされません。

order labels レイヤーの作成

手作業を含む mask の確認が終わった後に Create Order Labels を押すと、widgets/order_labels.py が現在の vein_mask と同じ shape の order_labels Labels レイヤーを作ります。現在の widget フローでは、この操作時に skeleton レイヤーは作りません。

作成後は vein_mask を非表示にし、order_labels を active な paint mode にします。order labels への描画は確認済み mask の対象領域内だけに制限され、mask が後から変わった場合も領域外のラベルを 0 に戻します。

vein_mask は 1 = 葉脈（黄色、不透明度 0.5）、0 = 背景（透明）です。status 行に葉脈として塗られた割合を出し、45% を超えると葉身や背景を選んでいる疑いがあると知らせます。mask を手で直すときは label 1 で塗ると葉脈を足し、消しゴム（label 0）で葉脈を消せます。order labels は vein_mask > 0 の領域を分類対象とし、作成時にはその領域を label 4（uncertain）で初期化します。order labels を作った後に mask を直すと、mask から消えた部分のラベルは 0 に戻り、mask に足した部分は label 4（uncertain）になります。Export では order labels を vein_mask と照合し、mask にあるのに次数が 0 の画素があれば警告します。描画制限と後からの clipping も同じ条件を使うため、mask の値の向きを変更するときは order_labels.py 側も一緒に確認する必要があります。

葉脈が前景なので、Clean Mask の「Small object area」は小さな葉脈の断片を、「Maximum hole area」は葉脈の内側の小さな穴を対象にします。穴埋めを大きくすると小さな網目（areole）まで潰れるため、既定値は 50 px にしています。

order labels の値は、次の用途を想定しています。

label 意味
0 背景または分類対象外
1 primary
2 secondary
3 tertiary（3次脈）
4 uncertain / 未分類

同じ shape の order labels レイヤーがすでにある場合は、ユーザーが手で塗った内容を上書きせず、そのレイヤーを再利用します。

1次・2次脈の自動振り分け

auto_order.py（napari に依存しない）が、Manual of Leaf Architecture（Ellis et al., 2009）の次数の決め方を骨格のグラフの上で行います。ユーザーは葉の基部と1次脈の先端を2回クリックするだけです。

段階 処理 Ellis の対応する記述
1次脈 基部から先端まで、1歩のコストを「長さ ÷ 直径²」とした最短経路 1次脈は最も太く、基部から先端へ走る
2次脈の候補 1次脈の縁のすぐ外の輪で、出ていく枝の太さを測る。同じ側の近くで最も太い枝の 70% 以上なら候補 次数は付け根の最も太い所で判断する。2次脈は先端へ向かって細くなるので、固定の境目は使わない
2次脈の走り方 同じ側の葉縁まで最短経路でたどり、太さが急に落ちた所で切る ほぼ同じ太さで続く脈は同じ次数
3次脈の除外 たどった経路の大半がより太い2次脈と重なる候補は、1次と2次をつなぐ3次脈として外す 3次脈は1次・2次脈どうしをつなぐ

距離の設定は mm で持ち、校正値で画素に直すので、解像度が変わっても同じ規則が使えます。3200 dpi のコナラ標本では、1次脈と約30本の2次脈が取れ、基部付近の脈は手で直す必要がありました。結果は不確定（4）の画素にだけ書き込み、クリック位置・設定・本数を order_labels.auto_order としてメタデータに残します。

PlantPose（Liu et al., 2026）のような学習ベースの骨格推定は木構造を出力し、ループや次数、細い脈の太さを扱わないため、ここでは使っていません。

Export の実行

Export Measurements ボタンは書き出しを別スレッドで実行し、その間も napari を操作できます（widgets/measurement.py）。

  1. prepare_export() がメインスレッドでレイヤーと入力欄を読み、ラベル・mask・元画像のコピーを ExportJob にまとめる。
  2. run_export_job() が別スレッドで骨格化、長さの計測、ファイル書き出しを行う。napari のレイヤーや Qt には触れない。
  3. 終わったら通知を出し、ボタンを元に戻す。

3200 dpi の葉全体（約 3,900 × 8,400 px）では計測と骨格の表で約 30 秒かかります。葉身全体が mask になっていた場合は骨格化に3分以上かかっていました。直径は distance_transform_edt で求めます（medial_axis と同じ「背景までの距離」で、より速い）。

再現性のためのメタデータ

Export のたびに <時刻>_<画像名>_metadata.yaml を書き出し、同じ Export のファイルには同じ接頭辞を付けます。設定ファイルは「既定値」にすぎず、実際にはスライダーで閾値を動かしたり、mask を手で直したりするため、各工程で実際に使った値をレイヤーの metadata に記録しておき、それをまとめて書き出します。

項目 内容
source_image 元画像のパス、SHA-256、shape
calibration mm/px、校正方法、入力値と単位
leaf_area 確定マスク由来なら画素数・SHA-256・標本状態・ROI範囲・mm²、外部入力なら入力値・単位・mm²
order_labels.processing ROI 範囲、Gaussian sigma、Otsu 値、最終閾値と invert、Clean Mask の全実行（各回の値と、その前に手修正があったか）
mask_edited_by_hand_after_last_step 最後の自動処理の後に mask を手で直したか（内容のハッシュで判定）
label_pixel_counts ほか 次数ごとの画素数、未分類・次数なしの画素数
vein_paths 次数ごとのパス本数
settings 使っていた設定ファイルと、その時点の既定値
software Python と主要パッケージのバージョン

手で直した mask はパラメータからは再現できないため、*_vein_mask.npy として mask 自体も保存します。

設定ファイル

各入力欄の既定値は、widget を開いたときに YAML の設定ファイルから読み込みます（settings.py）。リポジトリには推奨値を書いた leaf_vein_workflow.example.yaml が入っています。

  • リポジトリのフォルダで napari を起動し、leaf_vein_workflow.yaml がなければ、example をコピーして作ります。値を変えたいときはこの leaf_vein_workflow.yaml を編集します。
  • leaf_vein_workflow.yaml は git の管理外なので、自分の値がコミットされたり、更新とぶつかったりしません。
  • 推奨値に戻したいときは、example を leaf_vein_workflow.yaml に上書きコピーします（Reset to Defaults でも同じ）。
  • 別のフォルダから起動したときは、ユーザーごとの config.yaml を使います。

使っているファイルの場所は Settings セクションに表示されます。

キー 推奨値 内容
calibration.method / value dpi / 1200 校正方法と値。2次脈の太さを測れる解像度を推奨値にしている
scale_bar.length_mm 10 Apply Scale 後に描く表示用バーの長さ
mask.gaussian_sigma / invert_threshold 1.0 / false 平滑化と閾値の向き（向きは Apply Otsu が自動で上書き）
mask.exclude_background true ROI に葉の周りの背景が含まれる前提で、2段階の Otsu を使う
cleanup.* 100 / 50 / 1 / 0 px 葉脈片の除去、穴埋め、closing、opening
measurement.leaf_area_unit / output_dir mm2 / output 葉面積の単位と出力先（相対パスは起動フォルダ基準）

ファイルに書いたキーだけが推奨値を上書きします。書いていないキーや不正な値は推奨値に戻り、不正な値には警告を出します。Open Settings File はファイルがなければ推奨値入りのコメント付きファイルを作って開き、Reload で編集を反映し、Reset to Defaults で推奨値のファイルに戻します（元のファイルは *.bak に残す）。

計測と VLA

パス計測（1次・2次）

参考プロトコル（Sack & Scoffoni 2013）では、1次脈と 2次脈は葉全体の画像で segmented line としてなぞり、長さを合計して葉面積で割ります。vein_paths.py はこの方法に対応します（今は dock に表示していません）。Draw Vein Paths を押すと元画像に <画像名> vein paths の Shapes レイヤーができ、path 描画モードになります。クリックで頂点を置き、ダブルクリックで1本を確定します。

各パスは order feature（1 または 2）を持ち、新しいパスには dock で選んだ次数が付きます。既存のパスを選択して次数を切り替えると付け替わり、色（1次 = 赤橙、2次 = 青）も更新されます。長さは頂点間の距離の合計で、校正値は元画像から引き継ぎます。Export Measurements で *_path_measurements.csv（次数ごとの本数・長さ・VLA）と、全頂点を記録した *_path_vertices.csv を書き出します。3次脈は葉全体ではなく矩形の標本領域で測る方法なので、パス計測の対象にしていません。

次数ラベル計測

widgets/measurement.py が order.py の measure_order_labels を呼び、label 1・2・3 をそれぞれ別に骨格化して skan の branch 長を合計します。合算行（primary_secondary = 1+2、major = 1+2+3）は、単一次数の長さの和です。合併領域を骨格化し直すと次数の境界で骨格が短くなり、major が primary より短くなることがあるためです。major を 1–3 次とする定義は Sack & Scoffoni (2013) に従っています。

葉面積は既定の確認フローでは同じROIの確定葉身マスクから計算します。外部入力は別の選択肢として保持し、明示的に切り替えた場合だけ使います。標本化前の面積は標本の葉脈長と状態が異なり得るため、収縮補正と混同しません。確定マスク選択時には計測済み面積を表示し、外部面積の入力欄と単位欄は非表示にします。外部入力へ切り替えたときだけ入力欄を表示し、値を切り替えの間も保持します。外部値をcm²で入力した場合は100倍してmm²に換算します。VLA は length_mm / leaf_area_mm2 で、apply_leaf_area により長さを保ったまま葉面積だけ差し替えられます。CSV には leaf_area_source 列で葉面積の出どころ（input または leaf_mask）を残します。label 4 のまま残ったピクセルはどの次数にも入らず、結果欄に件数を警告として出します。

エラーや警告になる例

次の場合は、切り抜き処理に進まず、警告またはエラーになります。

状況 理由
校正値が0以下、NaN、inf 実単位へ安全に換算できない
スケールバー線がない、または2本以上ある どの線長を使うか決められない
ROI レイヤー以外を選択している どの ROI を使うか分からない
ROI が 0 個 切り抜く範囲がない
ROI が 2 個以上 MVP では 1 個だけ対応
ROI が長方形ではない MVP では rectangle のみ対応
ROI が画像と重ならない 切り抜ける画素がない
画像が 2D grayscale または RGB/RGBA ではない MVP の対応範囲外
crop レイヤーがまだない状態で Apply Gaussian を押す 平滑化する画像がない
Apply Gaussian 前 Apply Otsu control がまだ無効になっている
vein_mask 作成前に Clean Mask または Create Order Labels を押す 処理対象の mask がない
crop 画像に NaN や inf が含まれる 閾値計算が信用できない

テストで確認していること

tests/test_calibration.py では、DPI・µm/px・mm/px・手動スケールバーからの換算、無効値の拒否、校正metadataだけを派生レイヤー用にコピーできることを確認しています。

tests/test_crop.py では、napari に依存しない切り抜き計算を確認しています。

  • 小数座標が floor と ceil で正しく slice になること。
  • 画像外にはみ出た ROI が画像範囲に切り詰められること。
  • RGB 画像の色チャンネルが保たれること。
  • 空の ROI や画像外 ROI がエラーになること。
  • 未対応の画像 shape がエラーになること。

tests/test_threshold.py では、napari に依存しない二値化計算を確認しています。

  • grayscale 画像をそのまま float の 2D 配列として扱えること。
  • RGB/RGBA 画像を grayscale に変換できること。
  • Gaussian smoothing が入力と同じ shape の 2D 画像を返すこと。
  • 手動閾値で明るい前景と暗い前景の両方を mask にできること。
  • Otsu 閾値が単純な二峰性画像を分けられること。
  • small object removal、hole filling、closing、opening で mask を整えられること。
  • 未対応の画像 shape がエラーになること。

現在の widget フローからは骨格化を呼びませんが、独立した計算 helper の回帰確認として tests/test_skeleton.py は残っています。

  • 2D mask から骨格画像を作れること。
  • Labels 形式の整数 mask でも、0 より大きい画素を前景として扱うこと。
  • 空 mask や 2D 以外の入力がエラーになること。
  • 校正値を渡すと既存px列を変えずに長さ・直径・局所座標のmm列が追加されること。

tests/test_widget_import.py では、Qt backend がある環境で _widget.py から widget を import できることと、画像追加から order labels までの工程を確認しています。

  • Add ROI 後に crop が active になり、元画像が非表示になること。
  • Apply Gaussian では smoothed_image だけが作られ、vein_mask はまだ存在しないこと。
  • Apply Otsu では葉身候補だけが作られ、葉身の確定後に葉脈maskが作られて閾値UIで更新できること。
  • Clean Mask 後も mask が active な paint mode に保たれること。
  • order labels が mask 外に描けず、既存の手動ラベルが再作成時に上書きされないこと。
  • ROI を切り直すと古い派生レイヤーが削除されること。
  • 数値入力と手動スケールバーの校正値が派生レイヤーへ継承され、再校正で置き換わること。

まとめ

現在の実装は、葉脈解析そのものではなく、葉脈解析の前段階として「人が ROI を指定し、Gaussian と Otsu を明示的に適用し、mask を cleanup と手作業で確認してから、葉脈次数を塗り分ける」ための機能です。

設計上は、napari 依存の処理も UI、レイヤー管理、ROI、mask、order labels に分かれ、NumPy ベースの計算処理とも分離されています。manifest 互換性は _widget.py、widget 全体の接続は crop_widget.py、個々の工程は対応する担当モジュールから読み始めればよく、1 ファイルの内部を端から探す必要はありません。

確定葉身マスクはExport時に *_leaf_mask.npy として保存します。全葉のpath計測にはROI面積を自動流用せず、外部面積を明示的に指定します。
