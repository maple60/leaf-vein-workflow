Leaf Vein Workflow の挙動と関数の流れ

このノートの目的

このノートは、leaf-vein-workflow の現在の MVP 実装について、人間が読んで流れを理解するための説明です。

このプラグインが今やることは、次の 3 段階に絞られています。

  • napari で画像を開き、長方形 ROI を 1 つ描き、Add ROI ボタンを押したときだけ、その範囲の切り抜き画像レイヤーを作る。
  • 切り抜き画像に Gaussian smoothing を適用し、Otsu 閾値で葉脈候補の mask Labels レイヤーを作り、形態学的処理と手作業で整える。
  • 確認済みの mask Labels レイヤーから、手動分類用の order labels レイヤーを作る。

まだ扱わないことは、複数 ROI、ポリゴン ROI、画像の保存、nD stack、骨格のセグメンテーション、VLA の計算、major/minor の自動分離です。

ユーザーから見た流れ

ユーザー操作としては、次の順番になります。

  1. napari を起動する。
  2. Plugins > Leaf Vein Workflow > Leaf Vein Workflow から widget を開く。
  3. napari 標準の方法で葉画像を開く。
  4. プラグインが自動で ROI 用の Shapes レイヤーを作る。
  5. 画像上に長方形を 1 つ描く。
  6. Add ROI ボタンを押す。
  7. 長方形の範囲だけを切り抜いた Image レイヤーが追加される。
  8. Gaussian sigma を確認して Apply Gaussian を押す。
  9. 平滑化した smoothed_image Image レイヤーだけが作られる。
  10. Apply Otsu を押すと、初めて vein_mask Labels レイヤーが作られる。
  11. 必要なら Invert threshold と Mask threshold を調整する。変更後、少し待つと同じ mask レイヤーが更新される。
  12. 形態学的処理の値を確認して Clean Mask を押す。
  13. paint mode の vein_mask を手作業で修正する。
  14. mask を確認した後に Create Order Labels を押す。
  15. order_labels Labels レイヤー上で葉脈次数を塗り分ける。

重要なのは、各工程がユーザーの操作で明示的に区切られている点です。長方形を描いただけでは crop は作られず、Apply Gaussian を押しても vein_mask は作られません。mask が初めて作られるのは Apply Otsu を押したときです。

全体像

napari 上では 1 つの dock widget ですが、実装は人間が担当範囲を追いやすいように責務別に分かれています。

ファイル 役割
src/leaf_vein_workflow/_widget.py manifest と既存 import のために CropWidget と定数を再公開する入口
src/leaf_vein_workflow/widgets/crop_widget.py 1 つの widget を組み立て、signal を接続し、公開メソッドを各担当へ委譲する
src/leaf_vein_workflow/widgets/controls.py ボタンや入力欄を作り、工程ごとの有効・無効を管理する
src/leaf_vein_workflow/widgets/layers.py metadata、レイヤー間の対応、検索、選択、削除を一元管理する
src/leaf_vein_workflow/widgets/roi.py 画像の検出、ROI Shapes レイヤー、crop の作成を担当する
src/leaf_vein_workflow/widgets/mask.py Gaussian、Otsu、閾値更新、Clean Mask を担当する
src/leaf_vein_workflow/widgets/order_labels.py order labels の作成と mask 外への描画防止を担当する
src/leaf_vein_workflow/crop.py 画像配列をどこで切るかを計算する
src/leaf_vein_workflow/threshold.py grayscale 化、Gaussian、閾値、mask cleanup を NumPy 配列に対して計算する
src/leaf_vein_workflow/order.py order labels の検証、集計、export に使う napari 非依存の処理を置く

初心者向けに言うと、_widget.py は変わらない「玄関」、crop_widget.py は全体をつなぐ「進行係」、widgets/ の残りは工程別の「担当者」です。crop.py、threshold.py、order.py は napari の画面を直接触らない「計算の係」です。

napari への登録

napari は src/leaf_vein_workflow/napari.yaml を読んで、このパッケージの widget を見つけます。

このファイルでは、leaf_vein_workflow._widget:CropWidget が widget として登録されています。つまり napari のメニューからプラグインを開くと、CropWidget クラスが作られます。

CropWidget の初期化

CropWidget は、napari に渡す 1 つの dock widget です。実際のクラスは widgets/crop_widget.py にあり、_widget.py は従来と同じ import 先を保つためにそれを再公開します。

作られた直後に、主に次の準備をします。

  • napari viewer を self.viewer に保存する。
  • controls.py でボタン、入力欄、ステータス表示を作る。
  • layers.py で ROI、crop、smoothed image、mask、order labels の対応関係を管理する。
  • ROI、mask、order labels の各担当に、共有する controls とレイヤー管理を明示的に渡す。
  • crop_widget.py でボタンや Qt signal を各担当の処理へ接続する。
  • 新しく追加された画像と、すでに開かれている画像の両方を ROI 担当に渡す。

CropWidget の add_roi()、apply_gaussian_filter()、use_otsu_threshold()、clean_mask()、create_order_labels() は、既存コードやテストから同じ名前で呼べます。ただし実処理は対応する工程モジュールへ委譲されます。これにより、画面は 1 つのままでも、修正時に読む範囲を絞れます。

画像が追加されたとき

画像レイヤーが追加されると、crop_widget.py がその event を roi.py の画像準備処理へ渡します。

ROI 担当は、次の確認をします。

  1. 追加されたレイヤーが napari の Image レイヤーか。
  2. その画像が、プラグイン自身が作った crop レイヤーではないか。
  3. すでに ROI レイヤーと結びついている画像ではないか。

この確認を通った画像だけに、ROI 用の Shapes レイヤーを作ります。

ROI レイヤーには、metadata として次の情報が入ります。

metadata 意味
leaf_vein_workflow_role = roi_shapes この Shapes レイヤーは ROI 用である
source_image = 元画像名 どの画像から作られた ROI か

さらに、layers.py のレイヤー管理が、ROI レイヤーと元画像レイヤーの対応を保存します。各工程が個別の対応表を持たないため、派生レイヤーを探す規則や削除する順序を 1 箇所で確認できます。

ROI が編集されたとき

ユーザーが ROI を描いたり編集したりすると、roi.py の ROI 確認処理が呼ばれます。

ここで確認しているのは、主に次の 2 点です。

  • ROI が 1 つだけあるか。
  • その ROI が長方形か。

ROI が 0 個、または 2 個以上ある場合は、ステータス表示で「長方形を 1 つだけ描いてください」と案内します。長方形以外の場合は、警告を出します。

ただし、この段階ではまだ画像を切り抜きません。ここでは「準備ができたか」を確認しているだけです。

Add ROI を押したとき

Add ROI ボタンを押すと、公開メソッド CropWidget.add_roi() が roi.py の切り抜き処理へ委譲します。

ROI 担当は、まず次の順番でチェックします。

  1. 現在選択されているレイヤーが ROI 用 Shapes レイヤーか。
  2. その ROI レイヤーが元画像と結びついているか。
  3. ROI が 1 つだけか。
  4. ROI が長方形か。
  5. ROI が画像と重なっているか。

すべて通った場合だけ、実際の切り抜き処理に進みます。

切り抜き処理では、rectangle_to_slices() と crop_to_rectangle() の 2 つを使います。

rectangle_to_slices()

rectangle_to_slices() は、ROI の頂点座標を NumPy の slice に変換する関数です。

たとえば、長方形 ROI の座標がだいたい次の範囲だったとします。

座標 値
y の最小値 1.2
y の最大値 3.7
x の最小値 2.1
x の最大値 4.9

この場合、関数は次のように整数の範囲へ変換します。

軸 変換後
y slice(1, 4)
x slice(2, 5)

最小値側は floor で下に丸め、最大値側は ceil で上に丸めます。これにより、ROI に含まれる画素を取りこぼしにくくしています。

また、ROI が画像の外にはみ出している場合は、画像の範囲内に切り詰めます。完全に画像と重ならない場合は、エラーにします。

対応している画像は、現在の MVP では次の 2 種類です。

  • 2D grayscale image
  • 2D RGB/RGBA image

crop_to_rectangle()

crop_to_rectangle() は、実際に画像配列を切り抜く関数です。

内部では、まず rectangle_to_slices() を呼び出して、切り抜く y 範囲と x 範囲を決めます。その後、画像が 2D なら次のように切ります。

image_array[y_slice, x_slice]

RGB/RGBA のように最後の軸が色チャンネルの場合は、色チャンネルを残すために次のように切ります。

image_array[y_slice, x_slice, :]

戻り値は .copy() された配列です。これは、元画像の一部を参照するのではなく、切り抜き画像として独立したデータにするためです。

crop レイヤーの作成と更新

ROI 担当は、切り抜いた画像を napari の Image レイヤーとして追加します。

新規作成時には、次の情報を指定します。

  • レイヤー名は 元画像名 ROI
  • RGB/RGBA 画像なら rgb=True
  • translate に ROI の左上位置を入れる
  • metadata に crop レイヤーであることを記録する

translate を設定する理由は、切り抜き画像を元画像上の ROI 位置に重ねて表示しやすくするためです。

同じ ROI レイヤーからすでに crop レイヤーが作られている場合は、新しいレイヤーを増やさず、既存レイヤーの data と translate を更新します。

crop を作り直した場合は、古い crop から派生した smoothed_image、vein_mask、order_labels を削除します。新しい範囲に古い解析結果が残らないようにするためです。その後、crop を active layer にし、元画像を非表示にします。

mask レイヤーの作成と更新

mask 処理は widgets/mask.py が担当し、Apply Gaussian、Apply Otsu、Clean Mask という明示的な工程に分かれています。

Apply Gaussian は、現在の crop Image レイヤーに threshold.py の smooth_image() を適用し、smoothed_image Image レイヤーだけを作成または更新します。この時点では vein_mask を作りません。Gaussian sigma の初期値は 1 で、必要に応じて実行前に変更できます。

Apply Otsu は、平滑化済み画像から otsu_threshold() で閾値を推定します。その閾値を使って threshold_image() を実行し、ここで初めて vein_mask Labels レイヤーを作成します。二値化の前には to_grayscale() で画像を 2D grayscale に変換し、RGB/RGBA 画像では alpha を無視します。

Invert threshold が有効な場合は、閾値以下の画素を 1 として扱います。これは、葉脈が背景より暗い画像で使う想定です。

一度 Apply Otsu を実行した後は、閾値入力欄、slider、Invert threshold の変更に応じて同じ mask を更新します。連続した UI signal ごとに重い処理を繰り返さないよう、短い待ち時間を置く single-shot timer で更新をまとめます。この timer にも「Otsu 実行済み」の確認があり、control の初期化や Apply Gaussian だけで mask が作られることを防ぎます。

mask は napari の Labels レイヤーとして作られます。レイヤー名は vein_mask です。同じ crop レイヤーからすでに mask が作られている場合は、新しいレイヤーを増やさず、既存 mask レイヤーの data と translate を更新します。

Clean Mask は、small object removal、hole filling、closing、opening の設定を postprocess_mask() に渡し、現在の mask を明示的に整えます。cleanup 後は自動の閾値更新を止め、vein_mask を active な paint mode に保ちます。これにより、その後の手作業による修正が遅延 timer で上書きされません。

order labels レイヤーの作成

手作業を含む mask の確認が終わった後に Create Order Labels を押すと、widgets/order_labels.py が現在の vein_mask と同じ shape の order_labels Labels レイヤーを作ります。現在の widget フローでは、この操作時に skeleton レイヤーは作りません。

作成後は vein_mask を非表示にし、order_labels を active な paint mode にします。order labels への描画は確認済み mask の対象領域内だけに制限され、mask が後から変わった場合も領域外のラベルを 0 に戻します。

現在の実装では、vein_mask == 0 の white-out 領域を分類対象とし、作成時にはその領域を label 4（uncertain）で初期化します。描画制限と後からの clipping も同じ条件を使うため、mask の値の向きを変更するときは order_labels.py 側も一緒に確認する必要があります。

order labels の値は、次の用途を想定しています。

label 意味
0 背景または分類対象外
1 primary
2 secondary
3 minor
4 uncertain / 未分類

同じ shape の order labels レイヤーがすでにある場合は、ユーザーが手で塗った内容を上書きせず、そのレイヤーを再利用します。

エラーや警告になる例

次の場合は、切り抜き処理に進まず、警告またはエラーになります。

状況 理由
ROI レイヤー以外を選択している どの ROI を使うか分からない
ROI が 0 個 切り抜く範囲がない
ROI が 2 個以上 MVP では 1 個だけ対応
ROI が長方形ではない MVP では rectangle のみ対応
ROI が画像と重ならない 切り抜ける画素がない
画像が 2D grayscale または RGB/RGBA ではない MVP の対応範囲外
crop レイヤーがまだない状態で Apply Gaussian を押す 平滑化する画像がない
Apply Gaussian 前 Apply Otsu control がまだ無効になっている
vein_mask 作成前に Clean Mask または Create Order Labels を押す 処理対象の mask がない
crop 画像に NaN や inf が含まれる 閾値計算が信用できない

テストで確認していること

tests/test_crop.py では、napari に依存しない切り抜き計算を確認しています。

  • 小数座標が floor と ceil で正しく slice になること。
  • 画像外にはみ出た ROI が画像範囲に切り詰められること。
  • RGB 画像の色チャンネルが保たれること。
  • 空の ROI や画像外 ROI がエラーになること。
  • 未対応の画像 shape がエラーになること。

tests/test_threshold.py では、napari に依存しない二値化計算を確認しています。

  • grayscale 画像をそのまま float の 2D 配列として扱えること。
  • RGB/RGBA 画像を grayscale に変換できること。
  • Gaussian smoothing が入力と同じ shape の 2D 画像を返すこと。
  • 手動閾値で明るい前景と暗い前景の両方を mask にできること。
  • Otsu 閾値が単純な二峰性画像を分けられること。
  • small object removal、hole filling、closing、opening で mask を整えられること。
  • 未対応の画像 shape がエラーになること。

現在の widget フローからは骨格化を呼びませんが、独立した計算 helper の回帰確認として tests/test_skeleton.py は残っています。

  • 2D mask から骨格画像を作れること。
  • Labels 形式の整数 mask でも、0 より大きい画素を前景として扱うこと。
  • 空 mask や 2D 以外の入力がエラーになること。

tests/test_widget_import.py では、Qt backend がある環境で _widget.py から widget を import できることと、画像追加から order labels までの工程を確認しています。

  • Add ROI 後に crop が active になり、元画像が非表示になること。
  • Apply Gaussian では smoothed_image だけが作られ、vein_mask はまだ存在しないこと。
  • Apply Otsu 後に初めて mask が作られ、閾値 UI で更新できること。
  • Clean Mask 後も mask が active な paint mode に保たれること。
  • order labels が mask 外に描けず、既存の手動ラベルが再作成時に上書きされないこと。
  • ROI を切り直すと古い派生レイヤーが削除されること。

開発時に見る順番

挙動を追うときは、次の順番で読むと理解しやすいです。

  1. README.md でユーザー操作を確認する。
  2. src/leaf_vein_workflow/napari.yaml で widget 登録を確認する。
  3. src/leaf_vein_workflow/_widget.py で互換用の公開入口を確認する。
  4. widgets/crop_widget.py で 1 つの widget の組み立て、signal 接続、各工程への委譲を見る。
  5. widgets/controls.py で UI 部品と有効・無効の切り替えを見る。
  6. widgets/layers.py で metadata、レイヤー間の対応、active/visible、削除の規則を見る。
  7. widgets/roi.py と crop.py で画像追加、ROI 編集、切り抜き処理を見る。
  8. widgets/mask.py と threshold.py で Gaussian、Otsu、timer、cleanup の流れを見る。
  9. widgets/order_labels.py で order labels の作成と描画制限を見て、必要なら order.py で検証、集計、export 処理を見る。
  10. tests/test_widget_import.py で、これらが 1 つの明示的な操作フローとして接続されていることを確認する。

まとめ

現在の実装は、葉脈解析そのものではなく、葉脈解析の前段階として「人が ROI を指定し、Gaussian と Otsu を明示的に適用し、mask を cleanup と手作業で確認してから、葉脈次数を塗り分ける」ための機能です。

設計上は、napari 依存の処理も UI、レイヤー管理、ROI、mask、order labels に分かれ、NumPy ベースの計算処理とも分離されています。manifest 互換性は _widget.py、widget 全体の接続は crop_widget.py、個々の工程は対応する担当モジュールから読み始めればよく、1 ファイルの内部を端から探す必要はありません。
